3.1

外设与 I/O

I/O：物理世界怎么进程序

外设是 CPU 之外、用来感知或驱动外部世界的硬件模块——传感器、LED、风扇驱动等都算。I/O（Input/Output）是程序与这些硬件打交道的总称：输入把外界变成程序里的数，输出把程序里的决定变成外界动作。

物理世界 电气层 软件层 温度 / 按键 → 电压 / 电平 → 驱动读寄存器或缓冲 LED / 风扇 ← 高/低、开关 ← 程序写「开/关」

同一条 GPIO 脚，配置成输出就能驱动 LED；配置成输入就能读按键。传感器、执行器再复杂，对用户态程序来说，最终仍是「读到一个值」或「写出一个命令」。下一节我们会把这根脚在 Linux 里的名字（chip / line）和本板的 1.8 V 电平讲清楚——否则「写了 1 却不见亮」会很难排查。

寄存器、MMIO 与用户态边界

寄存器是芯片内部一组可读写的控制位，用来配置外设、读状态、写输出。MMIO（Memory-Mapped I/O，内存映射 I/O）把这些寄存器映射到 CPU 可见的地址空间：驱动对某个地址的读写，实际落到外设控制逻辑，而不是普通 RAM。

说法含义本课怎么用
MMIO用「访存」方式访问设备寄存器建立心智；用户态程序不直接写这些地址做业务
设备节点如 /dev/gpiochip0应用通过 open / 库 API 访问
内核驱动独占硬件、做权限与时序管理保证多进程安全、屏蔽芯片细节
应用 C 代码 │ gpiod_* / open / ioctl ▼ 设备节点（/dev/...） │ 系统调用 ▼ 内核驱动 ──► MMIO 寄存器 ──► 物理引脚 / 外设
记住一句：板上有 MMIO，但本课业务程序走内核暴露的接口（如 gpiod）。「深入理解」会用 devmem 只读核对某一位是否翻转，用来对照理解驱动写了寄存器——不拿它当日常控灯手段。
安全边界：不要把 GPIO 接到市电或大电流负载；风扇等执行器必须经继电器或驱动模块，GPIO 只控信号端。另外：荔枝派 4A 的原生 GPIO 逻辑电平是 1.8 V（不是常见的 3.3 V）——接 3.3 V 模块时要做电平匹配，细节在 3.2。
本节成果：能口述物理世界 → 电气 → 软件的路径 · 理解 MMIO 与用户态 API 的分工。
3.2

GPIO：用 gpiod 控灯与继电器

这一节我们把「外设」落到一根具体的脚上。读完你应该能回答四个问题：GPIO 是什么、Linux 怎么给脚编号、高低电平在本板上意味着什么、为什么程序要先「申请」才能改电平。灯和继电器只是同一套道理的两种负载。

一根脚能做什么

GPIO（General-Purpose Input/Output，通用输入输出）是芯片上可以由软件配置方向的引脚。配置成输出时，程序决定它是高还是低，外面的世界跟着变（灯亮灭、继电器吸合）。配置成输入时，程序去读外面世界此刻是高还是低（按键有没有按下）。

对学生来说，最有用的心智模型是：

  • 输出＝程序对世界说话：「请亮」「请灭」。
  • 输入＝程序听世界说话：「现在按下了吗？」
  • 同一根物理脚，同一时刻通常只做一件事：要么说，要么听。

风扇、传感器模块看起来很复杂，但对 GPIO 这一层，常常仍然是「某一根脚输出高/低」或「某一根脚按规则被拉高/拉低」。复杂被拆进了模块内部；你的程序首先要会管好自己的那根脚。

Linux 怎么称呼一根脚：chip 与 line

一块板子上往往有多组 GPIO 控制器。Linux 把每一组暴露成一个字符设备，名字像 /dev/gpiochip0、/dev/gpiochip1……每一个叫一个 gpiochip（芯片控制器节点，不一定等于「整颗 SoC」）。

在某一个 chip 里面，脚按编号排列，这个编号叫 line（线号 / offset）。本课默认控灯、控风扇信号脚用的是：

#define GPIO_CHIP_PATH  "/dev/gpiochip1"
#define LED_LINE        3    /* 对应排针丝印 IO1_3；换脚只改数字 */

请把这两个名字一起记住：chip 告诉你在哪一组控制器上，line 告诉你是这一组里的第几根。只说「GPIO3」而不说 chip，在多控制器的板上会说不清到底是哪一根；只说 chip 不说 line，内核也不知道你要哪一根。

说法指什么本课例子
排针丝印硬件手册上的名字，接线时认这个IO1_3、IO1_4
/dev/gpiochipN内核暴露的某一组 GPIO 控制器gpiochip1
line 编号该 chip 内从 0 起的偏移line 3 → IO1_3
内核 debug 全局号/sys/kernel/debug/gpio 里的 gpio-538 一类基址 + line；不要和 line 数字混用
为什么 debug 里看到 gpio-538，程序却写 line 3？内核会给全板 GPIO 分配一段全局编号（基址因内核版本而变）。gpiochip1 若从 535 起算，则 line 3 对应全局号 538。日常编程用 chip + line；debug 文件用来排查「到底谁占着这根脚」，不要把 538 抄进 C 宏当 line。再提醒一句：gpiochipN 的 N 由内核按探测顺序动态分配，换个镜像（如如意 OS / RevyOS）可能整体平移——默认镜像的 gpiochip1，在别处未必还是它。换系统后第一件事是重新认脚（见下方「故障排查」）。
排针丝印 IO1_3 │ （查课程接线表） ▼ /dev/gpiochip1 的 line 3 │ ▼ 内核里可能显示为 gpio-538（基址+3） │ ▼ 物理引脚电平 ←→ LED / 继电器信号端

「高」「低」在本板上是什么意思

程序里写 1 / 0（或 active / inactive），最终变成引脚上的电压：

  • 高（high）：接近该脚所在电源域的电压。
  • 低（low）：接近地（GND）。

许多教材默认「GPIO = 3.3 V」。荔枝派 4A 不是：官方说明里，SoC 原生 IO 为 1.8 V。排针上的 3.3 V / 5 V 电源脚是给外设供电的，不等于信号脚也是 3.3 V。

你接什么1.8 V GPIO 通常能不能直接扛本课态度
红光 LED + 限流电阻常常可以（灯可能偏暗）讲义 blink、验证「程序能动世界」的首选
按键到 GND（内部上拉）可以学输入输入实验可用
常见 3.3 V/5 V 继电器信号端、DHT22 数据线常常带不动或电平不匹配需要电平转换（见 lab）；不要用杜邦线硬怼长期试验

电平转换板（芯片型号常见为 TXS0108E，课里就叫电平转换板）做的事很单一：在「板子说的 1.8 V」和「模块听的 3.3 V」之间当翻译。它不测温、不转风扇，也不负责「把电流喂给模块」——电压翻译对了，不代表电流也够；继电器信号端要毫安级电流，翻译板常常喂不动。风扇仍由继电器触点去开关电源。接线细节与验收步骤在 lab.html，这里先建立「为什么需要翻译」。

共地：无论灯、按键还是模块，板子的 GND 与外设 GND 必须连在一起。没有公共地，「高」「低」没有共同参考，现象会随机、难复现。

向内核借一根脚：gpiod / libgpiod

在 Linux 用户态，你不直接去改芯片寄存器来控日常业务。你向内核说：「我想使用 gpiochip1 的 line 3，请把它配成输出，初始为低。」内核同意后，你再请求「请设为高」「请设为低」。这套用户态库和命令行工具，统称 gpiod（库名常见 libgpiod，链接 -lgpiod）。

你的 C 程序 │ 打开 chip → 取得 line → 申请方向 → 读写电平 → 用完释放 ▼ libgpiod │ 系统调用 ▼ 内核 GPIO 子系统 / 驱动 │ 真正写 MMIO、改引脚 ▼ 物理脚 ──► LED /（经电平转换后）继电器信号端

为什么要绕这一圈？因为同一根脚可能被别的进程、某个内核驱动、或你上次没退干净的命令占用。内核统一仲裁，才不会两个人各写各的、互相踩。日常控灯、控继电器信号端，走 gpiod；「深入理解」里用 devmem 只读核对寄存器位，那是旁路验证，不是第二条业务路径。

板端常见的配套命令（版本不同，参数写法略有差异；本课板子多为 libgpiod 2.x）：

  • gpioinfo：看某个 chip 上每根 line 的方向、有没有被占用、占用者名字。
  • gpioset：申请并保持某根脚为指定电平（进程活着时通常一直占着）。
  • gpioget：读电平——若该脚正被别人以输出方式占用，往往会失败。

注意：许多板上没有名叫 gpio 的万能命令；看到的是上面这一组。需要权限时用 sudo，或把用户加入 gpio 组（以课程环境为准）。

/* 讲义 blink 的骨架：打开 → 申请输出 → 翻转 → 释放 */
chip = gpiod_chip_open("/dev/gpiochip1");
line = gpiod_chip_get_line(chip, 3);
gpiod_line_request_output(line, "ch03-blink", 0);  /* 消费者名字会出现在占用信息里 */
gpiod_line_set_value(line, 1);   /* 高 */
gpiod_line_set_value(line, 0);   /* 低 */
gpiod_line_release(line);
gpiod_chip_close(chip);
消费者名字（consumer）不是装饰。申请时传入的字符串会出现在 gpioinfo / debug/gpio 里。调试「谁占着我的脚」时，能一眼看出是 gpioset、ch03-blink 还是别的程序——所以起名要诚实。

独占与「Device or resource busy」

GPIO line 在 Linux 上通常是独占申请的：同一时刻，一个成功的「请求」占住这根脚，别人再申请或用另一种方式去读，就可能得到 Device or resource busy 或打不开。

这不是板子坏了，而是规则在起作用。课堂上最常见的情况是：

  1. 你用 gpioset 把脚设成高或低做试验，命令一直占着不退出；
  2. 随后再跑 blink、再 gpioget，全部失败；
  3. 查占用信息，会看到 consumer 写成 gpioset，方向是 output，电平是 lo 或 hi。

处理思路也很「嵌入式」：先弄清谁占着，再决定是结束那个进程，还是改用另一根 line。不要同时开两个程序抢同一根脚「看谁赢」——赢的是内核的报错，输的是你的耐心。

正常： 程序 A 申请 line 3 → 使用 → 释放 → 程序 B 才能再申请 踩坑： gpioset 占着 line 3=0 不退出 │ ▼ blink / gpioget → busy（对的，该拒绝）

灯与继电器：同一套 GPIO，两种负载

灯是最小执行器：电流很小，适合验证「我的 chip/line 选对了、程序真的改到了电平」。本课讲义跟做以 LED 为准——看见亮灭，GPIO 故事才算落地。

继电器把「小信号」变成「能不能给大电流通路通电」：GPIO（往往再经电平转换）只驱动继电器的信号端（丝印可能是 IN / X1）；风扇电机的电源走继电器触点（NO / COM 一类）。你的程序仍然只是在写高/低，并没有「直接驱动电机」。

对象GPIO 在做什么你要建立的直觉
LED输出高/低 → 灯亮/灭程序 ↔ 物理世界的最短闭环
继电器 → 风扇输出高/低 → 信号端有效 → 触点通断电源GPIO 管命令；大电流不进 SoC 脚

实验里风扇、DHT22、电平转换如何接线，以 lab.html 为准。讲义这一节只要求你：先会用 gpiod 诚实地点亮一盏灯；继电器是同一 API 换负载，不是另一套「风扇专用系统调用」。

跟做 blink：让一根脚学会眨眼

chapters/ch03/code/blink/ 做的事只有一件：按规定的 chip/line 申请输出，然后周期翻转高低。你要验证的不是「命令背得熟」，而是三件事同时成立：

  1. 宏里的 chip、line 与排针接线一致；
  2. 交叉编译出的程序在板上能打开 gpiochip（权限够）；
  3. LED 真的闪——世界响应了程序。
  1. 1
    认脚
    打开接线表，确认你插的是哪根排针，对应 gpiochip? 与 line ?。改 main.c 里的宏，不要猜。
  2. 2
    先排除「被占用」
    若板上刚做过手动拉高/拉低，先确认没有残留的 gpioset 占着同一 line，否则 blink 会申请失败。
  3. 3
    交叉编译并上板运行
    主机 make → scp → 板端运行。预期：灯周期性闪烁，终端有 [INFO] blinking line …。
  4. 4
    灯不闪时怎么想
    顺序建议：脚号/接线 → 共地与限流电阻 → 程序是否申请成功 → 是否 1.8 V 驱动不动该负载。先别跳到改内核或乱写寄存器。

故障排查：继电器不动，问题在哪一环？

这不是一张命令清单，而是一条排查思路。它来自真实案例：程序明明写了「高」，继电器却纹丝不动。我们把它当侦探案，顺着信号链逐环找证据，最后发现——我们从头到尾在驱动一根并不在排针上的脚。换模块、换线、换电压全都没用，因为信号根本没到排针。

先建心智模型：信号要走过五环

① 程序想做的事 ② 内核状态 ③ 编号 ↔ 排针 ④ 引脚电压 ⑤ 模块与接线 "我想拉高" → 谁占着？什么值？ → 这个 chip/line 是不是那根针 → 真有 1.8V？ → 共地？吃得动？ │ │ │ │ ▼ ▼ ▼ ▼ ps 看进程 debug 看状态 pinmux 查映射 万用表/LED 拔线对照

继电器不动，问题一定出在这五环之一。排查不是挨个重试——换个模块、再插一遍、多按几下——而是每一环都拿到证据，把看不见的中间环节逐段点亮。断在哪一环，就修哪一环。

第一环：你的程序到底写了什么？

先别碰硬件。登录板子，看「现在到底是谁占着脚、写的是什么值」。板端没有叫 gpio 的万能命令，而是这一组：

$ ps aux | grep gpioset
$ sudo cat /sys/kernel/debug/gpio

真实的教训：ps 显示好几个 sudo gpioset -c gpiochip1 3=0 一直挂着，而 debug 文件里那根 line 写得清清楚楚——out lo。你以为拉了高，实际写的是 0；而且进程一直占着脚不退出。软件段已经错了两处：值写错、进程没清。「我记得是高的」不是证据，ps 和 debug 文件才是。顺带：非 root 读这些会 Permission denied，所以都用 sudo。

第二环：占脚的进程怎么清？

结束残留进程，第一个想到 pkill。这里有个会咬人的坑：

$ pkill -f gpioset   # ❌ 会匹配到自己的命令行，把自己也杀了
$ pkill -x gpioset   # ✅ 精确按进程名匹配，只杀 gpioset

为什么？-f 匹配整条命令行，而 pkill -f gpioset 这串字符里就含「gpioset」，于是它匹配到了自己（连同包着它的 shell），没执行完就自尽了，后面的步骤全没跑。换成 -x 按进程名精确匹配就安全。

第三环：这编号，真的是那根针吗？

这是本案例的总根因，也是最有价值的一课。教程写着 /dev/gpiochip1 line 3——但它只在默认镜像里成立。gpiochip 的编号是内核按探测顺序动态分配的，换个镜像就整体平移。本课这块板跑如意 OS（RevyOS），查 pinmux 立刻现形：

$ sudo cat /sys/kernel/debug/pinctrl/*/pinmux-pins

结果：排针上那 4 个 GPIO（丝印 IO1_3/4/5/6）在 gpiochip5（地址 0xffec006000，GPIO1 组）；而我们一直在操作的 gpiochip1（地址 0xfffff52000）是板子内部的另一个控制器，根本不在排针上。

教程写的RevyOS 内核里的真相结果
/dev/gpiochip1 line 3gpiochip1＝内部控制器；排针 GPIO 在 gpiochip5一直在驱动一根不在排针上的脚 → 继电器永远不动

这一条解释了此前的全部困惑：换 TXS、换直连、换电压全都不行——因为信号根本没到排针。死记教程的 chip 编号，等于对着过期的地图找路。

教训：排针丝印（IO1_3）是硬件事实，稳定不变；(chip, line) 是内核动态编号，随镜像/内核而变。认脚要认丝印，编号要查运行时。换了系统，第一件事就是重新确认 chip/line，别照抄旧教程。

第四环：给「看不见的高/低」一个可见证据

软件说高，不等于引脚上真有电压。最直接的是万用表：红笔接目标脚、黑笔接 GND，程序写 1 应读到约 1.8 V（本板 GPIO 电平），写 0 读到 0 V。没有万用表时，用一颗红 LED 当探针——但 1.8 V 直接喂红 LED 常常点不亮（它的导通电压就压在 1.8–2 V 附近），所以改成 3.3 V 供电、让 GPIO 当开关：

3.3V ──► 红LED ──► 电阻（约 330Ω）──► GPIO 脚（LED 负极朝 GPIO）

GPIO 低(0V)   → LED 亮
GPIO 高(1.8V) → 压差只剩 1.5V → LED 灭

来回写高/低，看灯亮灭切换，就用眼睛「看见」了软件在动——它瞬间戳破「我以为高了」的错觉。

第五环：还剩一种可能——脚被外部拉住

真实排查里我们还遇到一根脚怎么拉都是低：程序写 1，debug 里仍是 out lo。这时别怀疑内核坏了，先做对照实验：把连在这根脚上的模块全部拔掉再测。拔掉后能拉高，就是外部电路（某根线、某个模块、共地接错）把它拖到地；拔掉后仍拉不高，才是脚本身或配置的问题。这一步把「板子 vs 接线」干净地切成两半。

整条思路一句话：先软件后硬件，每一环都拿证据、不靠猜。程序 → 内核状态 → 编号↔排针 → 引脚电压 → 模块接线，五环逐段点亮，断在哪修哪。顺带记住两个事实：chip 编号是活的（换系统要重认）；电平转换板是翻译器不是电源（它管电压、不管电流，喂不动要吃毫安的继电器光耦）。
本节成果：能用自己的话解释 chip/line、高低电平与本板 1.8 V · 理解为何要经 gpiod 申请且会 busy · 用 blink 点亮 LED · 能说明继电器只是「GPIO 命令 + 大电流电闸」 · 会用信号链五环做故障排查（ps / pkill -x / debug 文件 / 万用表或 LED 探针）。
3.3

温控闭环

传感 → 决策 → 执行

DHT22 是温湿度探头，用一根数据线接 GPIO，周期上报温度和湿度。它按严格时序一位一位收发数据；时序稍紧或线上干扰时，用户态读取可能偶发失败——属预期：打 [ERR] 并进入下一采样周期，让程序继续跑。

执行侧本课主线是开/关：GPIO 高/低 → 继电器 → 风扇电源通断。两档阈值形成滞回（第二章已定义：中间区间保持上一状态），避免温度在临界附近风扇狂抖。

DHT22 ──► 温度 T │ ▼ 阈值判断 T > T_HIGH → 风扇开（继电器吸合） T < T_LOW → 风扇关（继电器释放） 中间区间 → 保持上一状态 │ ▼ gpiod 写 FAN_LINE ──► 继电器信号端 ──► 风扇
/* 伪代码：完整主循环在 lab 的 temp-fan 里落地 */
if (读温度失败) { 打 [ERR]; 继续下一轮; }
else if (T > T_HIGH) 风扇_开();
else if (T < T_LOW)  风扇_关();

本节成果：能说清 DHT22 → 阈值 → 继电器 → 风扇的数据流。下一节深入理解用 devmem 只读核对「写灯时寄存器位真的翻了」。
深入理解

gpiod 写灯之后：内核如何翻寄存器位，以及你如何亲眼看见

原因：用户态 API 并不直接碰芯片寄存器

你在 C 里调用 gpiod_line_set_value(line, 1)，看起来只是「把灯打开」。真正改硬件的，是内核里的 GPIO 驱动：它通过系统调用接到你的请求后，往某个 MMIO 地址写一笔，把对应引脚那一位从 0 翻成 1（或反过来）。引脚电平变了，LED 才亮。

回顾几个词，串成一条链：

  • GPIO：通用输入输出引脚；Linux 上用 chip + line 定位，本课用来输出高/低控灯或继电器信号端。
  • 继电器：小信号开关大电流；GPIO 只管信号，风扇电源走继电器触点。
  • MMIO：设备寄存器被映射成「像内存一样」的地址；驱动对地址的写，落到硬件控制逻辑。
  • devmem：按物理地址读/写内存映射区域的小工具。本课只读，用来核对某一位是否翻转，绝不拿它当日常控灯手段。
① 应用：gpiod_line_set_value(..., 1) │ 经 libgpiod → 打开的 /dev/gpiochipN │ 系统调用进入内核 ▼ ② 内核 GPIO 驱动 │ 写 MMIO：把该引脚对应的 bit 置 1（或清 0） ▼ ③ 硬件寄存器（某物理地址上的一个字） │ ▼ ④ 物理引脚电平变高 / 变低 ──► LED 亮 / 灭 旁路核对（只读，不当业务路径）： 点灯前：devmem 读该寄存器 → 记下那一位是 0 点灯后：devmem 再读同一地址 → 那一位变成 1

读图：左边主路径是业务程序该走的路——永远经 gpiod / 内核。右边旁路是课堂验证：你不改驱动源码，也能用只读 devmem 看见「那一位确实翻了」，从而相信主路径终点落在寄存器上。

机制落地：点灯前后各读一次

寄存器地址与「哪一位对应哪根脚」来自芯片手册与板卡文档，本课由当堂下发（具体 0x…… 与 bit 编号以课堂材料为准，勿自行猜测）。你要做的是固定同一地址、同一位，做前后对比。

  1. 1
    先用 gpiod 控灯
    跑 blink，或写一个只置一次高/低的小程序，确认 LED 有可见变化。没有可见变化时，先查接线与 line 编号，不要先怪寄存器。
  2. 2
    拿到课堂给出的地址与 bit
    例如：某 GPIO 数据寄存器物理地址 0xADDRESS，你的 LED 对应第 N 位。把地址和 N 记在实验记录里。
  3. 3
    点灯前只读一次
    sudo devmem 0xADDRESS 32，得到一个 32 位十六进制值。按课堂说明标出第 N 位当前是 0 还是 1。
  4. 4
    点灯后再读同一地址
    保持其他条件不变，只改变 gpiod 写出的电平，再跑一次 devmem。对比：第 N 位应随灯的亮灭翻转；其余位通常不变（若变了，说明读错地址或脚位映射理解有误）。
# 地址与位以课堂下发为准；以下仅为命令形态
$ sudo devmem 0xADDRESS 32
# 例如输出：0x00000000  → 记下第 N 位

# 用 gpiod 把灯打开（blink 或单独 set）

$ sudo devmem 0xADDRESS 32
# 例如输出：0x00020000  → 同一第 N 位已翻
纪律：本课对 MMIO 只做 devmem 读。不要用它写寄存器控灯——会与内核驱动抢硬件，行为不可预期，也可能把脚配成危险状态。

对照：内核驱动里「写寄存器」的那一行

课堂会指出（或投影）内核 GPIO 驱动中与「写数据寄存器」对应的那一行——形态往往是「读出旧值 → 改某一 bit → 写回」或直接写置位/清零寄存器。你不需要在本课改内核；目的是把三件事对齐：

用户态一行： gpiod_line_set_value(line, 1); 内核驱动一行（课堂指出的写寄存器语句）： 写 MMIO → 改变第 N 位; 你亲眼看见： devmem 前后对比 → 第 N 位 0→1（或 1→0） LED 同时亮灭变化

读图：上层 API、驱动写语句、硬件位、肉眼可见的灯，四者应同时一致。若灯亮了但位没变，多半是地址/位号对错了脚；若位变了灯不亮，多半是接线或高低电平有效极性问题——回到 3.2 查硬件，而不是怀疑「Linux 魔法」。

整条故事：gpiod 写灯 → 系统调用 → 内核 GPIO 驱动写 MMIO → 寄存器某一 bit 翻转 → 引脚电平变 → LED 亮；用 devmem 只读在点灯前后核对同一 bit，并对照课堂给出的驱动写寄存器那一行。

本节成果：能口述 GPIO / 继电器 / MMIO / devmem · 能用 blink + devmem 只读完成位翻转对照 · 带着概念进入本章实验组装完整温控闭环。
