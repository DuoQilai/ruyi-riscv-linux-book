3.1

外设与 I/O

I/O：物理世界怎么进程序

外设是 CPU 之外、用来感知或驱动外部世界的硬件模块——传感器、LED、风扇驱动等都算。I/O（Input/Output）是程序与这些硬件打交道的总称：输入把外界变成程序里的数，输出把程序里的决定变成外界动作。

物理世界 电气层 软件层 温度 / 按键 → 电压 / 电平 → 驱动读寄存器或缓冲 继电器 / 风扇 ← 高/低、开关 ← 程序写「开/关」

同一条 GPIO 脚，配置成输出就能驱动执行器（如继电器、风扇的信号端）；配置成输入就能读按键。执行器再复杂，对用户态程序来说，最终仍是「写出一个命令」。下一节我们会把这根脚在 Linux 里的名字（chip / line）和本板的 1.8 V 电平讲清楚——否则「写了 1 却不见动」会很难排查。

寄存器、MMIO 与用户态边界

寄存器是芯片内部一组可读写的控制位，用来配置外设、读状态、写输出。MMIO（Memory-Mapped I/O，内存映射 I/O）把这些寄存器映射到 CPU 可见的地址空间：驱动对某个地址的读写，实际落到外设控制逻辑，而不是普通 RAM。

说法含义本课怎么用
MMIO用「访存」方式访问设备寄存器建立心智；用户态程序不直接写这些地址做业务
设备节点如 /dev/gpiochip0应用通过 open / 库 API 访问
内核驱动独占硬件、做权限与时序管理保证多进程安全、屏蔽芯片细节
应用 C 代码 │ gpiod_* / open / ioctl ▼ 设备节点（/dev/...） │ 系统调用 ▼ 内核驱动 ──► MMIO 寄存器 ──► 物理引脚 / 外设
记住一句：板上有 MMIO，但本课业务程序走内核暴露的接口（如 gpiod）。「深入理解」会用 devmem 只读核对某一位是否翻转，用来对照理解驱动写了寄存器——不拿它当日常控外设手段。
安全边界：不要把 GPIO 接到市电或大电流负载；风扇等执行器必须经继电器或驱动模块，GPIO 只控信号端。另外：荔枝派 4A 的原生 GPIO 逻辑电平是 1.8 V（不是常见的 3.3 V）。本课继电器是光耦隔离的，1.8 V 直连即可；需要电平匹配的模块我们到第四章再说。
本节成果：能口述物理世界 → 电气 → 软件的路径 · 理解 MMIO 与用户态 API 的分工。
想一想：用户态程序为什么不直接读写 MMIO 寄存器，而要经过 gpiod / 内核接口？ 因为内核统一仲裁「谁占着这根脚」、屏蔽芯片细节、做权限管理。直接写会跟别的进程或驱动抢硬件——我们排查 busy 时看到过：GPIO 是独占申请的。这正是「用户态 API → 内核 → MMIO」这条链存在的意义。
3.2

GPIO：用 gpiod 控继电器与风扇

这一节我们把「外设」落到一根具体的脚上。读完你应该能回答四个问题：GPIO 是什么、Linux 怎么给脚编号、高低电平在本板上意味着什么、为什么程序要先「申请」才能改电平。继电器和风扇是这套道理落地的地方。

一根脚能做什么

GPIO（General-Purpose Input/Output，通用输入输出）是芯片上可以由软件配置方向的引脚。配置成输出时，程序决定它是高还是低，外面的世界跟着变（继电器吸合、风扇转）。配置成输入时，程序去读外面世界此刻是高还是低（按键有没有按下）。

对学生来说，最有用的心智模型是：

  • 输出＝程序对世界说话：「请吸合」「请释放」。
  • 输入＝程序听世界说话：「现在按下了吗？」
  • 同一根物理脚，同一时刻通常只做一件事：要么说，要么听。

风扇、传感器模块看起来很复杂，但对 GPIO 这一层，常常仍然是「某一根脚输出高/低」或「某一根脚按规则被拉高/拉低」。复杂被拆进了模块内部；你的程序首先要会管好自己的那根脚。

Linux 怎么称呼一根脚：chip 与 line

一块板子上往往有多组 GPIO 控制器。Linux 把每一组暴露成一个字符设备，名字像 /dev/gpiochip0、/dev/gpiochip1……每一个叫一个 gpiochip（芯片控制器节点，不一定等于「整颗 SoC」）。

在某一个 chip 里面，脚按编号排列，这个编号叫 line（线号 / offset）。本课默认控继电器/风扇信号脚用的是：

#define GPIO_CHIP_PATH  "/dev/gpiochip5"
#define FAN_LINE        5    /* 对应排针丝印 IO1_5；换脚只改数字 */

请把这两个名字一起记住：chip 告诉你在哪一组控制器上，line 告诉你是这一组里的第几根。只说「GPIO3」而不说 chip，在多控制器的板上会说不清到底是哪一根；只说 chip 不说 line，内核也不知道你要哪一根。

说法指什么本课例子
排针丝印硬件手册上的名字，接线时认这个IO1_5、IO1_6
/dev/gpiochipN内核暴露的某一组 GPIO 控制器gpiochip5
line 编号该 chip 内从 0 起的偏移line 5 → IO1_5
内核 debug 全局号/sys/kernel/debug/gpio 里的 gpio-651 一类基址 + line；不要和 line 数字混用
为什么 debug 里看到 gpio-651，程序却写 line 5？内核会给全板 GPIO 分配一段全局编号（基址因内核版本而变）。gpiochip5 在本板从 646 起算，则 line 5 对应全局号 651。日常编程用 chip + line；debug 文件用来排查「到底谁占着这根脚」，不要把 651 抄进 C 宏当 line。再提醒一句：gpiochipN 的 N 由内核按探测顺序动态分配，换个镜像（如如意 OS / RevyOS）可能整体平移——教程写的 gpiochip1，在别处未必还是它。换系统后第一件事是重新认脚（见下方「故障排查」）。
排针丝印 IO1_5 │ （查课程接线表） ▼ /dev/gpiochip5 的 line 5 │ ▼ 内核里可能显示为 gpio-651（基址+5） │ ▼ 物理引脚电平 ←→ 继电器信号端

「高」「低」在本板上是什么意思

程序里写 1 / 0（或 active / inactive），最终变成引脚上的电压：

  • 高（high）：接近该脚所在电源域的电压。
  • 低（low）：接近地（GND）。

许多教材默认「GPIO = 3.3 V」。荔枝派 4A 不是：官方说明里，SoC 原生 IO 为 1.8 V。排针上的 3.3 V / 5 V 电源脚是给外设供电的，不等于信号脚也是 3.3 V。

你接什么1.8 V GPIO 能不能直接扛本课态度
本课继电器（5V 光耦隔离模块）可以：输入侧就是一颗光耦 LED，1.8 V 足够触发直连 GPIO（IO1_5），不需要电平转换
需要 3.3 V/5 V 电平的传感器（如第四章的 DHT22）不行：高电平不够、还可能超压第四章再讲电平转换模块

为什么继电器能直连？因为它是光耦隔离的：输入侧只是一颗光耦 LED，1.8 V 就能点亮并触发内部继电器；而模块自己的 5 V 线圈与输入信号在电气上不相通，所以不存在电平打架。反过来，某些传感器（如 DHT22）的数据线要 3.3 V 电平，直接接 1.8 V 脚会「叫不醒、还可能烧脚」——那部分留到第四章。

共地：无论继电器还是任何模块，板子的 GND 与外设 GND 必须连在一起。没有公共地，「高」「低」没有共同参考，现象会随机、难复现。
想一想：1.8V 直连就能驱动这个继电器，为什么不用电平转换？ 因为它是光耦隔离的：输入侧就一颗 LED（光耦），1.8V 够点亮；模块自己的 5V 线圈和输入信号在电气上不相通，没有电平打架。要是换 3.3V 电平的传感器（第四章 DHT22），1.8V 就叫不醒、还可能烧脚——那时才需要 TXS。判断依据是「模块输入侧是什么」，不是「模块标了多少伏」。

向内核借一根脚：gpiod / libgpiod

在 Linux 用户态，你不直接去改芯片寄存器来控日常业务。你向内核说：「我想使用 gpiochip5 的 line 5，请把它配成输出，初始为低。」内核同意后，你再请求「请设为高」「请设为低」。这套用户态库和命令行工具，统称 gpiod（库名常见 libgpiod，链接 -lgpiod）。

你的 C 程序 │ 打开 chip → 配置 line → 申请 → 写电平 → 用完释放 ▼ libgpiod │ 系统调用 ▼ 内核 GPIO 子系统 / 驱动 │ 真正写 MMIO、改引脚 ▼ 物理脚 ──► 继电器信号端 ──► 风扇电源通断

为什么要绕这一圈？因为同一根脚可能被别的进程、某个内核驱动、或你上次没退干净的命令占用。内核统一仲裁，才不会两个人各写各的、互相踩。日常控继电器/风扇信号端，走 gpiod；「深入理解」里用 devmem 只读核对寄存器位，那是旁路验证，不是第二条业务路径。

板端常见的配套命令（版本不同，参数写法略有差异；本课板子多为 libgpiod 2.x）：

  • gpioinfo：看某个 chip 上每根 line 的方向、有没有被占用、占用者名字。
  • gpioset：申请并保持某根脚为指定电平（进程活着时通常一直占着）。
  • gpioget：读电平——若该脚正被别人以输出方式占用，往往会失败。

注意：许多板上没有名叫 gpio 的万能命令；看到的是上面这一组。需要权限时用 sudo，或把用户加入 gpio 组（以课程环境为准）。

/* temperature_fan 的核心（libgpiod v2；完整代码见 code/temperature-fan/） */
chip = gpiod_chip_open("/dev/gpiochip5");       /* 打开控制器 */
fan_req = line_request(FAN_LINE, OUTPUT, 0);  /* 申请 line 5 为输出，初始低（封装见代码） */
gpiod_line_request_set_value(fan_req, FAN_LINE, 1);   /* 高：继电器吸合 → 风扇转 */
gpiod_line_request_set_value(fan_req, FAN_LINE, 0);   /* 低：继电器释放 → 风扇停 */
gpiod_line_request_release(fan_req);                  /* 用完释放 */
消费者名字（consumer）不是装饰。申请时传入的字符串会出现在 gpioinfo / debug/gpio 里。调试「谁占着我的脚」时，能一眼看出是 gpioset、temperature-fan 还是别的程序——所以起名要诚实。

独占与「Device or resource busy」

GPIO line 在 Linux 上通常是独占申请的：同一时刻，一个成功的「请求」占住这根脚，别人再申请或用另一种方式去读，就可能得到 Device or resource busy 或打不开。

这不是板子坏了，而是规则在起作用。课堂上最常见的情况是：

  1. 你用 gpioset 把脚设成高或低做试验，命令一直占着不退出；
  2. 随后再跑 temperature_fan、再 gpioget，全部失败；
  3. 查占用信息，会看到 consumer 写成 gpioset，方向是 output，电平是 lo 或 hi。

处理思路也很「嵌入式」：先弄清谁占着，再决定是结束那个进程，还是改用另一根 line。不要同时开两个程序抢同一根脚「看谁赢」——赢的是内核的报错，输的是你的耐心。

正常： 程序 A 申请 line 5 → 使用 → 释放 → 程序 B 才能再申请 踩坑： gpioset 占着 line 5=0 不退出 │ ▼ temperature_fan / gpioget → busy（对的，该拒绝）

继电器与风扇：GPIO 命令 + 大电流电闸

继电器把「小信号」变成「能不能给大电流通路通电」：GPIO 直连驱动继电器的信号端（丝印 IN / X1，高电平吸合）；风扇电机的电源走继电器触点（NO / COM 一类）。你的程序仍然只是在写高/低，并没有「直接驱动电机」。

对象GPIO 在做什么你要建立的直觉
继电器 → 风扇输出高/低 → 信号端有效 → 触点通断 5V 电源GPIO 管命令；大电流不进 SoC 脚

接线细节以 lab.html 为准。讲义这一节只要求你：会用 gpiod 诚实地让继电器吸合/释放，让风扇跟着转。

故障排查：继电器不动，问题在哪一环？

这不是一张命令清单，而是一条排查思路。它来自真实案例：程序明明写了「高」，继电器却纹丝不动。我们把它当侦探案，顺着信号链逐环找证据，最后发现——我们从头到尾在驱动一根并不在排针上的脚。换模块、换线、换电压全都没用，因为信号根本没到排针。

先建心智模型：信号要走过五环

① 程序想做的事 ② 内核状态 ③ 编号 ↔ 排针 ④ 执行器响应 ⑤ 模块与接线 "我想拉高" → 谁占着？什么值？ → 这个 chip/line 是不是那根针 → 继电器动了吗？ → 共地？吃得动？ │ │ │ │ ▼ ▼ ▼ ▼ ps 看进程 debug 看状态 pinmux 查映射 软件状态/执行器 拔线对照

继电器不动，问题一定出在这五环之一。排查不是挨个重试——换个模块、再插一遍、多按几下——而是每一环都拿到证据，把看不见的中间环节逐段点亮。断在哪一环，就修哪一环。

第一环：你的程序到底写了什么？

先别碰硬件。登录板子，看「现在到底是谁占着脚、写的是什么值」。板端没有叫 gpio 的万能命令，而是这一组：

$ ps aux | grep gpioset
$ sudo cat /sys/kernel/debug/gpio

真实的教训：ps 显示好几个 sudo gpioset -c gpiochip1 3=0 一直挂着，而 debug 文件里那根 line 写得清清楚楚——out lo。你以为拉了高，实际写的是 0；而且进程一直占着脚不退出。软件段已经错了两处：值写错、进程没清。「我记得是高的」不是证据，ps 和 debug 文件才是。顺带：非 root 读这些会 Permission denied，所以都用 sudo。

第二环：占脚的进程怎么清？

结束残留进程，第一个想到 pkill。这里有个会咬人的坑：

$ pkill -f gpioset   # ❌ 会匹配到自己的命令行，把自己也杀了
$ pkill -x gpioset   # ✅ 精确按进程名匹配，只杀 gpioset

为什么？-f 匹配整条命令行，而 pkill -f gpioset 这串字符里就含「gpioset」，于是它匹配到了自己（连同包着它的 shell），没执行完就自尽了，后面的步骤全没跑。换成 -x 按进程名精确匹配就安全。

第三环：这编号，真的是那根针吗？

这是本案例的总根因，也是最有价值的一课。教程写着 /dev/gpiochip1 line 3——但它只在默认镜像里成立。gpiochip 的编号是内核按探测顺序动态分配的，换个镜像就整体平移。本课这块板跑如意 OS（RevyOS），查 pinmux 立刻现形：

$ sudo cat /sys/kernel/debug/pinctrl/*/pinmux-pins

结果：排针上那 4 个 GPIO（丝印 IO1_3/4/5/6）在 gpiochip5（地址 0xffec006000，GPIO1 组）；而我们一直在操作的 gpiochip1（地址 0xfffff52000）是板子内部的另一个控制器，根本不在排针上。

教程写的RevyOS 内核里的真相结果
/dev/gpiochip1 line 3gpiochip1＝内部控制器；排针 GPIO 在 gpiochip5一直在驱动一根不在排针上的脚 → 继电器永远不动

这一条解释了此前的全部困惑：换 TXS、换直连、换电压全都不行——因为信号根本没到排针。死记教程的 chip 编号，等于对着过期的地图找路。

教训：排针丝印（IO1_3）是硬件事实，稳定不变；(chip, line) 是内核动态编号，随镜像/内核而变。认脚要认丝印，编号要查运行时。换了系统，第一件事就是重新确认 chip/line，别照抄旧教程。
想一想：教程明明写着 gpiochip1，为什么你这块板不认？ 因为 gpiochip 编号由内核按探测顺序动态分配，换个镜像/内核版本就整体平移。教程按某一版镜像写的，不代表你的板子。别照抄——用 /sys/kernel/debug/gpio 和 pinmux 现场确认「排针 GPIO 到底在哪个 chip」。我们就是栽在 gpiochip1 上：信号打进了内部控制器，排针那根脚毫无反应。

第四环：让软件状态和执行器自己说话

软件说「高」还不够，要看两样东西对上：① 内核状态——/sys/kernel/debug/gpio 里那根 line 是 out hi 还是 out lo；② 执行器响应——继电器有没有「咔」、风扇转不转。软件写高 + 内核显示 hi + 继电器没动 → 问题在模块/接线那一环；软件写高 + 内核显示 lo → 问题在更前面。这样就把链条切成两段，一半一半地查。

第五环：脚被外部拉住，或这根脚本身就拉不高

真实案例：这块板子的 IO1_3 从没接过任何线，但程序写 1、debug 里它恒为 out lo——拉不高；同一条命令，IO1_4/5/6 全部正常。排除了接线后，这就是板级问题（引脚失效或板上有硬下拉）。做法不是修它，而是换一根脚，并把「实测哪根能用」记进实验记录。本课统一用 IO1_5（继电器）与 IO1_6（传感器），正是运行时验证后的结果——这就是前沿板卡要运行时查证的典型：教程说 IO1_3 是默认脚，但你的板子未必照办。

整条思路一句话：先软件后硬件，每一环都拿证据、不靠猜。程序 → 内核状态 → 编号↔排针 → 执行器响应 → 模块接线，五环逐段点亮，断在哪修哪。最重要的认知：chip/line 编号是活的（换系统要重认，认脚以丝印 + 运行时为准）；前沿板卡要运行时查证（教程会过期，实测为准）。
本节成果：能用自己的话解释 chip/line、高低电平与本板 1.8 V · 理解为何要经 gpiod 申请且会 busy · 用 temperature_fan 让继电器吸合、风扇转 · 会用信号链五环做故障排查（ps / pkill -x / debug 文件 / 执行器响应）· 明白前沿板卡要运行时查证。
想一想：排查「继电器不动」，为什么必须按「软件 → 硬件」顺序、不能先瞎换模块？ 每一环都要拿证据，断在哪修哪：①程序真写了高吗（ps 看进程和值）②内核状态（debug/gpio 是 out hi 还是 out lo）③chip/line 是不是排针（pinmux）④执行器动没动 ⑤模块接线（共地/供电/跳帽）。我们的真实教训是 chip 打到了内部控制器，还碰到一根脚本身拉不高——都靠运行时查证才定位。先换模块等于重头再来，浪费时间。
3.3

决策 → 执行：假温度怎么驱动风扇

数据流：决策 → 执行

第三章的程序不读任何传感器——温度是程序内部自己变的一段假温度（从 24°C 缓慢升到 31°C 再降回来），专门用来演示「决策 → 执行」这条链路：假温度 → 阈值判断 → 继电器 → 风扇。真传感器（DHT22）到第四章再接。

执行侧是开/关：GPIO 高/低 → 继电器 → 风扇电源通断。两档阈值形成滞回（第二章已定义：中间区间保持上一状态），避免温度在临界附近风扇狂抖。

假温度 T（程序内部自变） │ ▼ 阈值判断 T > T_HIGH → 风扇开（继电器吸合） T < T_LOW → 风扇关（继电器释放） 中间区间 → 保持上一状态 │ ▼ gpiod 写 FAN_LINE(IO1_5) ──► 继电器信号端 ──► 风扇
/* 伪代码：完整主循环在 code/temperature-fan 里落地 */
if (假温度 > T_HIGH) 风扇_开();
else if (假温度 < T_LOW)  风扇_关();

代码：chapters/ch03/code/temperature-fan/，阈值 T_HIGH=28 / T_LOW=26 可改。完整从零拼装（认零件、接线、验收）见 lab.html。

本节成果：能说清「决策（阈值判断）→ 执行（继电器 → 风扇）」的数据流，并理解滞回的意义。真传感器闭环到第四章再补。
想一想：为什么用两个阈值（滞回）而不是一个？ 一个阈值时，温度在临界附近抖一下，风扇就狂开狂关。两个阈值（高 28 开、低 26 关），中间区间保持上一状态，平滑不抖。真实温控都这么做——这是第三章就建立的控制逻辑心智。
深入理解

gpiod 写继电器之后：内核如何翻寄存器位，以及你如何亲眼看见

原因：用户态 API 并不直接碰芯片寄存器

你在 C 里调用 gpiod_line_set_value(line, 1)，看起来只是「让继电器吸合」。真正改硬件的，是内核里的 GPIO 驱动：它通过系统调用接到你的请求后，往某个 MMIO 地址写一笔，把对应引脚那一位从 0 翻成 1（或反过来）。引脚电平变了，继电器才吸合、风扇才转。

回顾几个词，串成一条链：

  • GPIO：通用输入输出引脚；Linux 上用 chip + line 定位，本课用来输出高/低控继电器/风扇信号端。
  • 继电器：小信号开关大电流；GPIO 只管信号，风扇电源走继电器触点。
  • MMIO：设备寄存器被映射成「像内存一样」的地址；驱动对地址的写，落到硬件控制逻辑。
  • devmem：按物理地址读/写内存映射区域的小工具。本课只读，用来核对某一位是否翻转，绝不拿它当日常控外设手段。
① 应用：gpiod_line_set_value(..., 1) │ 经 libgpiod → 打开的 /dev/gpiochipN │ 系统调用进入内核 ▼ ② 内核 GPIO 驱动 │ 写 MMIO：把该引脚对应的 bit 置 1（或清 0） ▼ ③ 硬件寄存器（某物理地址上的一个字） │ ▼ ④ 物理引脚电平变高 / 变低 ──► 继电器吸合/释放（风扇转/停） 旁路核对（只读，不当业务路径）： 改电平前：devmem 读该寄存器 → 记下那一位是 0 改电平后：devmem 再读同一地址 → 那一位变成 1

读图：左边主路径是业务程序该走的路——永远经 gpiod / 内核。右边旁路是课堂验证：你不改驱动源码，也能用只读 devmem 看见「那一位确实翻了」，从而相信主路径终点落在寄存器上。

机制落地：改电平前后各读一次

寄存器地址与「哪一位对应哪根脚」来自芯片手册与板卡文档，本课由当堂下发（具体 0x…… 与 bit 编号以课堂材料为准，勿自行猜测）。你要做的是固定同一地址、同一位，做前后对比。

  1. 1
    先用 gpiod 控继电器
    跑 temperature_fan，或写一个只置一次高/低的小程序，确认风扇有可见变化。没有可见变化时，先查接线与 line 编号，不要先怪寄存器。
  2. 2
    拿到课堂给出的地址与 bit
    例如：某 GPIO 数据寄存器物理地址 0xADDRESS，你的继电器信号脚对应第 N 位。把地址和 N 记在实验记录里。
  3. 3
    改电平前只读一次
    sudo devmem 0xADDRESS 32，得到一个 32 位十六进制值。按课堂说明标出第 N 位当前是 0 还是 1。
  4. 4
    改电平后再读同一地址
    保持其他条件不变，只改变 gpiod 写出的电平，再跑一次 devmem。对比：第 N 位应随继电器吸合/释放翻转；其余位通常不变（若变了，说明读错地址或脚位映射理解有误）。
# 地址与位以课堂下发为准；以下仅为命令形态
$ sudo devmem 0xADDRESS 32
# 例如输出：0x00000000  → 记下第 N 位

# 用 gpiod 把继电器吸合（temperature_fan 或单独 set）

$ sudo devmem 0xADDRESS 32
# 例如输出：0x00020000  → 同一第 N 位已翻
纪律：本课对 MMIO 只做 devmem 读。不要用它写寄存器控外设——会与内核驱动抢硬件，行为不可预期，也可能把脚配成危险状态。

对照：内核驱动里「写寄存器」的那一行

课堂会指出（或投影）内核 GPIO 驱动中与「写数据寄存器」对应的那一行——形态往往是「读出旧值 → 改某一 bit → 写回」或直接写置位/清零寄存器。你不需要在本课改内核；目的是把三件事对齐：

用户态一行： gpiod_line_set_value(line, 1); 内核驱动一行（课堂指出的写寄存器语句）： 写 MMIO → 改变第 N 位; 你亲眼看见： devmem 前后对比 → 第 N 位 0→1（或 1→0） 继电器吸合/释放、风扇转/停

读图：上层 API、驱动写语句、硬件位、执行器动作，四者应同时一致。若继电器动了但位没变，多半是地址/位号对错了脚；若位变了继电器没反应，多半是接线或高低电平有效极性问题——回到 3.2 查硬件，而不是怀疑「Linux 魔法」。

整条故事：gpiod 写继电器 → 系统调用 → 内核 GPIO 驱动写 MMIO → 寄存器某一 bit 翻转 → 引脚电平变 → 继电器吸合、风扇转；用 devmem 只读在改电平前后核对同一 bit，并对照课堂给出的驱动写寄存器那一行。

本节成果：能口述 GPIO / 继电器 / MMIO / devmem · 能用 temperature_fan + devmem 只读完成位翻转对照 · 带着概念进入本章实验组装完整温控闭环。
想一想：为什么 devmem 只读、绝不拿它写寄存器？ 写会绕过内核驱动直接碰硬件，和驱动抢寄存器、行为不可预期，还可能把脚配成危险状态。读是「旁路核对」——只用来证明「程序 → 内核 → 寄存器位」这条链真的发生过，不当业务手段。这也呼应 3.1 那条「业务走内核接口」的原则。
